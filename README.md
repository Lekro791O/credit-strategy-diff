# Система анализа изменений СПР — credit-strategy-diff

**Команда:** Red flags
**Состав:** Ионов Даниил · Раджабова Сабина · Снурницина Ксения · Черных Варвара
**Задача:** «Баланс-платформа» — хакатон НИЯУ МИФИ, 6–8 ноября. Модули 1–2
(сбор заявок, прогон через СПР) выданы организаторами как датасет; этот
репозиторий реализует модуль 3 (приведение и сравнение данных) и
модуль 4 (визуализация результатов в браузере).

Многопользовательское приложение: одни и те же заявки прогнаны через две
версии стратегии (BEFORE MASTER — прод, AFTER BETA — с изменением), приложение
показывает аналитику, **что изменилось, у кого и из-за чего** — до выката на прод.

---

## 1. Описание решения

Аналитик настраивает прогон (датасет, процедуры, проверки), запускает его в
фоне и за минуту получает ответ вместо ручной сверки тысяч документов.

Реализованный функционал:

- **Конфигурация прогона:** выбор датасета (демо 300 заявок, выданный датасет
  2002, загрузка своего zip), последовательность процедур, настройки
  нормализации (исключения, режимы массивов, бакеты), набор проверок и их
  параметры. Конфигурации сохраняются и запускаются повторно в один клик.
- **Пользовательский код двумя способами** (требование задания): редактируемая
  рабочая область в приложении или размещённый `.py`-файл по контракту
  `CHECK = {"id", "label", "params", "entrypoint"}`. Новая проверка применяется
  без изменения кода приложения.
- **Фоновый прогон с журналом этапов:** интерфейс не блокируется, видны
  этапы, процент готовности и код, исполнявшийся на каждом этапе. Состояние
  переживает перезагрузку страницы (*критерий задания).
- **Сводный отчёт:** число затронутых заявок и смен решений, матрица переходов
  «было → стало», разделение «логика стратегии vs входные данные», сводная
  таблица с изменяемой раскладкой поверх агрегированных фактов counts,
  переход от числа к списку заявок, к заявке и к атрибуту (до/после).
- **Отчёт проверок:** все проверки единой таблицей с вердиктами,
  фильтрами и переходами к заявкам; открытие по ссылке и скачивание в HTML со
  ссылкой обратно в сводный отчёт.
- **Мнение ИИ (опционально):** в LLM отправляется только компактная сводка
  (сдвиги решений, топ атрибутов, строки FAIL); модель недоступна — это
  показано явно, остальное работает.
- **Многопользовательность:** подписанные сессии, у каждого пользователя свои
  прогоны, конфигурации и рабочая область; чужой прогон по ссылке — 404.

## 2. Структура репозитория

```
api/            FastAPI-приложение: прогоны, конфигурации, витрина-запросы,
                журнал, экспорты (HTML-отчёт проверок, CSV витрины), LLM,
                загрузка датасетов, сессии (access.py), песочница (procedures.py)
frontend/       Одностраничный интерфейс без сборки: app.js, glossary.js
                (человекочитаемые подписи атрибутов), style.css
pipeline/       Модуль 3 (подписка 1): нормализация, сравнение, факты counts,
                качество данных; контракт Config/build_dataset
mart/           Хранение: DuckDB-витрина (вертикальный datamart), MartAPI,
                бенчмарки (benchmarks/REPORT.md)
checkrunner/    Изоляция пользовательского Python: Docker- или subprocess-
                песочница, контракт CHECK (подписка 2)
task/           Материалы организаторов: docs/, checks/ (5 выданных проверок),
                samples/, example/
scripts/        make_test_dataset.py — генератор синтетического датасета
                на 5000 заявок с эталоном истины (truth.csv)
tests/          Интеграционные тесты приложения и контрактов
data/           Рабочие данные (не в Git, кроме выданного датасета): прогоны,
                витрины, workspace, gigachat.json, llm.env
NOTES.md        Пояснительная записка по шаблону организаторов
```

## 3. Используемые технологии

- **Python 3.12+**, FastAPI + uvicorn — сервер, API, фоновые прогоны.
- **DuckDB 2.0** — хранение витрины (~290 тыс. строк на 2002 заявки):
  колоночная БД, индексы, материализованные факты counts.
- **vanilla JS + CSS** (без сборки, без внешних CDN — демо работает офлайн);
  собственный лёгкий pivot поверх серверных агрегатов.
- **checkrunner** — изоляция пользовательского кода: Docker по умолчанию,
  subprocess для доверенного локального кода (`CSD_TRUST_LOCAL_CODE=1`).
- **LLM (опционально):** OpenAI-совместимый интерфейс / GigaChat
  (OAuth, настройка в интерфейсе).
- **pytest** — 119 тестов (приложение, контракты, mart, checkrunner).

## 4. Данные

- `data/RUN-20260827-0001/` — выданный организаторами датасет: 2002 заявки,

- `scripts/make_test_dataset.py` — синтетический тест-набор 5000 заявок с

- Предобработка: нормализация JSON в плоскую таблицу сопоставляемых атрибутов
  (массивы — по ключам), исключение технических полей, бакетизация.

## 5. Архитектура и подход

Сквозной поток: **датасет → pipeline (нормализация → сравнение → факты) →
DuckDB-витрина → проверки → отчёты**.

- Вертикальный datamart по контракту `docs/СХЕМА_ВИТРИНЫ.md`: таблица
  `datamart` (UNION обеих срез, поле SOURCE), `attributes` (сопоставление,
  DIFF_FLAG по значению, не по бакету), слой разрезов `segments` (16 полей),
  представления `comparison` / `fact_members`, материализованная `counts`.
  Первичный ключ витрины: (APP_ID, PATH, ARRAY_KEY).
- Сводная таблица работает поверх агрегированных фактов counts и не сканирует
  витрину — поэтому открытие и смена раскладки занимают ~1 с на 2002 заявках.
- Итоги (totals/row/column) считаются сервером (COUNT DISTINCT), а не
  суммированием ячеек — заявка не задваивается между срезами.
- Проверки получают объект доступа MartAPI (`rows/count/app_ids/segments/
  total_apps`) и не знают о хранении; исполняются в песочнице.
- Многопользовательность: подписанные cookie-сессии (HMAC), владение
  проверяется middleware; состояние — на диске, прогоны переживают рестарт.
- Детали и замеры: см. `NOTES.md` и `mart/benchmarks/REPORT.md`.

## 6. Эксперименты и результаты

**Сверка с эталоном жюри (открытый датасет 2002 заявки):** совпадение точное,
расхождений 0 по всем заявкам и полям:

| Показатель | Наш прогон | Эталон |
|---|---:|---:|
| Заявок с различиями | 502 | 502 |
| Смен итогового решения | 385 | 385 |
| Решения до (APPROVE/REJECT) | 657 / 1345 | 657 / 1345 |
| Решения после | 496 / 1506 | 496 / 1506 |
| Скор БКИ, модель, порог по заявкам | совпали | — (все 2002 строки × 8 полей) |

**Трактовка `rules[].hit`:** `null` (не вычислялось) ≠ `false` (вычислено, не
сработало) — переход считается изменением; обоснование в `pipeline/BENCHMARK_HIT.md`.

**Производительность** (медианы, детали в `NOTES.md` и `mart/benchmarks/`):

| Операция | M4, macOS | Windows-ноутбук | Планка «хорошо» |
|---|---:|---:|---|
| Приведение + сравнение (build_dataset, 2002 заявки) | 5.2 с | 19 с | ≤ 2 мин |
| Полный цикл приложения (витрина в DuckDB + 5 проверок) | ~40 с | ~60 с | ≤ 2 мин |
| Открытие сводной (2002 заявки) | 1.2 с | ~1.0 с | ≤ 2 с |
| Drill: ячейка → список → заявка | 0.54 с | ~0.6–1.0 с | ≤ 1 с |
| Повторное открытие отчёта | 0.17 с | ~0.5 с | ≤ 1 с |

- Разница машин — обычная: M4 против ноутбучного 8-поточного Windows;
  в рамках одной машины все операции укладываются в планки «хорошо».
- Узкое место разбора — CPU-bound нормализация/сравнение JSON
  (8.7 с из 19 с на Windows); отчёт быстрый за счёт материализованных фактов.
- A/B-эксперимент с индексом `attr_app_lookup`: выигрыша не дал — отрицательный
  результат честно задокументирован в `mart/benchmarks/REPORT.md`.

## 7. Инструкция по запуску

Требования: Python 3.12+. Один процесс uvicorn; работает на macOS/Linux и
нативно на Windows (DuckDB-стек, subprocess-песочница).

```bash
# 1. зависимости
python -m venv .venv
.venv/Scripts/python -m pip install -r api/requirements.txt   # Windows
# source .venv/bin/activate && pip install -r api/requirements.txt  # Linux/macOS

# 2. запуск (фронтенд раздаётся тем же процессом)
.venv/Scripts/python -m uvicorn api.main:app --port 8000
# открыть http://localhost:8000
```

Пользовательский Python (процедуры и проверки «на лету») по умолчанию
исполняется в Docker-изоляции. Без Docker для локального демо:

```bash
# Windows
set CSD_TRUST_LOCAL_CODE=1
# Linux/macOS
export CSD_TRUST_LOCAL_CODE=1
```

Демо-режим работает без датасета (`demo://synthetic`, 300 заявок). Выданный
датасет уже лежит в репозитории: `data/RUN-20260827-0001` — выбирается в
списке датасетов. Последовательность демонстрации: см. раздел
«Сценарий демонстрации» ниже. Проверка корректности: `python -m pytest -q`.

### Настройка ИИ (опционально)

Форма «Подключить GigaChat» на главной странице (ключ хранится локально в
`data/gigachat.json`), либо файл `data/llm.env` / переменные окружения
`CSD_LLM_BASE_URL`, `CSD_LLM_API_KEY`, `CSD_LLM_MODEL` (OpenAI-совместимый
чат-интерфейс). Модель недоступна — вкладка «Мнение ИИ» показывает это явно.

### Сценарий демонстрации (по шагам задания, ~15 мин)

1. Конфигурация: датасет, порядок процедур, источник кода (встроенная /
   рабочая область / файл), проверки и параметры → «Запустить прогон».
2. Журнал этапов во время прогона: процент готовности, сообщения, «показать
   код этапа».
3. Итоги: 2002 заявок, 502 с различиями, 385 смен решения; матрица переходов;
   «логика vs входные данные».
4. Сводная таблица: раскладка по атрибутам и типам изменения, фильтры разрезов.
5. Детализация: клик по числу → список заявок → заявка → атрибут до/после.
6. Отчёт проверок: единая таблица вердиктов, фильтры, переходы к заявкам.
7. Новая проверка: рабочая область → код по контракту CHECK → «применить» →
   строка появляется в том же отчёте.
8. Экспорт: «скачать отчёт проверок (HTML)» → открыть файл → ссылка обратно в
   сводный отчёт приложения.
9. Архитектура: стек, витрина, песочница, замеры (см. NOTES.md).

## 8. Ограничения и развитие

- Инкрементальная догрузка данных во время прогона (помечено организаторами
  как необязательное) не реализована — витрина пополняемая, следующий шаг.
- Потоковое обновление отчёта «по мере поступления» — опционально, не делали.
- Парсер ответов покрывает целевой класс документов СПР (ограниченная глубина
  вложенности); новые типы ответов — через пользовательские процедуры.
- LLM — опциональный блок: без ключа приложение полностью работоспособно.
- Что дальше: параллельная нормализация (multiprocessing) для прогонов
  на 20 000+ заявок, версионирование пользовательских процедур, роли доступа.
