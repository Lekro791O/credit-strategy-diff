# credit-strategy-diff

Многопользовательское приложение для анализа изменений в системе принятия
решений (СПР): одни и те же заявки прогнаны через две версии стратегии
(BEFORE MASTER — прод, AFTER BETA — с изменением), и приложение показывает
аналитику, **что изменилось, у кого и из-за чего** — до выката на прод.

Задача от «Баланс-платформы» (Decision Flow) для хакатона, 6–8 ноября, НИЯУ МИФИ.
Модули 1–2 (сбор заявок, прогон через СПР) выданы как датасет — этот репозиторий
реализует модуль 3 (приведение и сравнение) и модуль 4 (визуализация).

## Возможности

- **Конфигурация прогона:** датасет, процедуры нормализации/сравнения/фактов,
  набор проверок и их параметры; конфигурации сохраняются и запускаются повторно.
- **Пользовательский код двумя способами:** рабочая область в приложении
  (редактор) или размещённый `.py`-файл по контракту
  `CHECK = {"id", "label", "params", "entrypoint"}` (см. `task/checks/README.md`).
  Новая проверка применяется без изменения кода приложения.
- **Фоновый прогон с журналом этапов:** интерфейс не блокируется, из журнала
  открывается код, исполнявшийся на этапе. Состояние переживает перезагрузку
  страницы.
- **Сводный отчёт:** число затронутых заявок и смен решений, сводная таблица
  с изменяемой раскладкой поверх фактов counts, переход от числа к списку
  заявок, к заявке и к атрибуту (значения до/после).
- **Отчёт проверок:** все проверки единой таблицей PASS/FAIL, LOW-CONFIDENCE
  подсвечены бледно, открытие по ссылке и скачивание в HTML со ссылкой
  на сводный отчёт приложения.
- **Мнение ИИ (опционально):** компактная сводка (агрегаты, FAIL-строки)
  отправляется в LLM; при недоступности модели интерфейс показывает это явно,
  остальное работает.

## Быстрый старт

Требования: Python 3.12+ (или Docker).

```bash
# 1. зависимости
python -m venv .venv
.venv/Scripts/python -m pip install -r api/requirements.txt   # Windows
# source .venv/bin/activate && pip install -r api/requirements.txt  # Linux/macOS

# 2. запуск (фронтенд раздаётся тем же процессом)
.venv/Scripts/python -m uvicorn api.main:app --port 8000
# открыть http://localhost:8000
```

Демо-режим работает без датасета (синтетические 300 заявок, пункт
`demo://synthetic` в выборе датасета). Для работы на выданном датасете
распакуйте его в `data/`:

```
data/RUN-20260827-0001/
├─ manifest.json
└─ RESULTS/
   ├─ BEFORE_MASTER/<APP_ID>.json
   └─ AFTER_BETA/<APP_ID>.json
```

Обработка датасета выполняется процедурами из `pipeline/` (подписка 1).
Интерфейс подключения: функция `build_mart(dataset_dir, normalize_cfg,
compare_cfg) -> (rows, segments)`, где `rows` — список dict по схеме
`task/docs/СХЕМА_ВИТРИНЫ.md`, `segments` — по слою разрезов. Пока pipeline
не готов, выбирайте демо-датасет.

Docker:

```bash
docker compose up --build     # http://localhost:8000, data/ проброшена в контейнер
```

## Настройка ИИ (опционально)

OpenAI-совместимый чат-интерфейс, через переменные окружения:

```bash
set CSD_LLM_BASE_URL=https://api.moonshot.ai/v1
set CSD_LLM_API_KEY=sk-...
set CSD_LLM_MODEL=kimi-k2-0711-preview
```

Без этих переменных вкладка «Мнение ИИ» показывает статус «недоступно»,
остальные функции не затронуты.

```bash
.venv/Scripts/python -m pytest tests/ -q    # 8 тестов: сквозной прогон, проверки, факты, экспорт
```

## Сценарий демонстрации (по шагам задания)

1. «Прогоны» → новый прогон: датасет, выданные 5 проверок с параметрами → Запустить.
2. Пока идёт — журнал этапов, кнопка «код этапа».
3. По завершении — сводка: всего / с различиями / смена решения.
4. «Сводная таблица»: раскладка по `path, change_type`, фильтры; клик по ячейке →
   заявки → заявка → атрибут до/после.
5. «Отчёт проверок»: строки FAIL, бледные LOW; «скачать HTML» → из файла ссылка
   на сводный отчёт.
6. «Рабочая область»: написать новую проверку → «применить к прогону» → строка
   попадает в тот же отчёт.
7. Два браузера с разными именами пользователей — многопользовательность.

## Структура и зоны

| Папка | Зона | Кто |
|---|---|---|
| `pipeline/` | Нормализация, сравнение, слой разрезов (модуль 3) | Codex 1 |
| `mart/` | Хранилище витрины + MartAPI (индексы, DuckDB) | Codex 2 |
| `checkrunner/` | Исполнение пользовательских проверок | Codex 2 |
| `api/` | FastAPI: прогоны, прогресс, workspace, экспорт, ИИ | Kimi |
| `frontend/` | Сводная таблица, отчёты, drill-down | Kimi |
| `task/` | Материалы организаторов: контракты, 5 проверок, примеры |

Правила: схемы данных — только из `task/docs/СХЕМА_ВИТРИНЫ.md` и
`task/checks/README.md`. Каждый пишет тесты на свою зону; эталонные CSV в
`task/example/` и `task/examples/` — фикстуры для тестов нормализации.
В `main` — через PR.

## Статус и известные ограничения

- Собрано из трёх подписок: `pipeline/` (нормализация, сравнение, разрезы),
  `mart/` + `checkrunner/` (DuckDB-хранилище и изоляция проверок), `api/` +
  `frontend/` (приложение). Сквозной прогон проверен на `task/samples`.
- Приложение предпочитает стек подписки 2: DuckDB-хранилище + проверки в
  изолированных процессах. На машинах без него (например, Windows —
  `mart.store` требует `fcntl`) автоматически используется встроенный
  SQLite-адаптер и исполнение проверок в процессе; интерфейс и результаты
  идентичны.
- Датасет организаторов (34 МБ) в git не входит — кладётся в `data/` локально;
  демо-режим (`demo://synthetic`) работает без него.
- Пользовательский код в фолбэке (SQLite) исполняется в процессе приложения;
  в основном режиме (DuckDB) — в отдельном процессе на проверку.
- Долгий прогон переживает перезагрузку страницы, но не перезапуск сервера
  между этапами.
