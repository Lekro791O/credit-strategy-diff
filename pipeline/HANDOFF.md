## Участнику 2: загрузка в хранилище и проверки

```python
from pipeline import run_directories

out = run_directories('task/samples/BEFORE', 'task/samples/AFTER')
comparison_rows = out['comparison']  # Iterable[dict], точная обязательная схема
segment_rows = out['segments']      # одна строка на APP_ID
# Ваш loader принимает эти два набора; MartAPI остаётся по task/checks/README.md.
```

Первичный ключ comparison: `(APP_ID, PATH, ARRAY_KEY)`. Все значения — строки,
кроме `DIFF_FLAG: int` (0/1). `CHANGE_TYPE` — четыре значения из ТЗ.
Потерянный/новый атрибут имеет пустые VALUE/ADJUSTED на отсутствующей стороне;
определять присутствие надо по CHANGE_TYPE, а не по `VALUE != ''`.
Настоящий JSON null — строка `NULL` (совместимость с
`check_stop_factor_disappeared.py`), логические значения — `true`/`false`.
Две исходные строки одинакового ключа вызывают ошибку до загрузки.

В segments обязательные поля — строки, кроме `DECISION_CHANGED: int`.
`PRODUCTS` — отсортированные уникальные product_id из product_trials обоих
срезов, через `;` (именно это ожидает `check_ar_drop_by_product.py`).
`PARTNER_TYPE` и `ROUTING_METHOD` — сортированный union обоих срезов через `;`.
`TOP_OFFER_*` — product_id оффера с наименьшим rank; при равенстве сортировка
по product_id и type. Отсутствующее значение — `''`.
`SCORE_OKB_*` берётся из `characteristics.score_okb`, не из features или ext_data.
Решение по заявке берётся из `decisionResult.decision`.

Несколько продуктов нельзя свести к случайному первому элементу:
`PD_MODEL_*`, `CUTOFF_*`, `REJECT_REASON_*` содержат общее значение, если оно
одно для всех продуктов. При разных значениях это **каноническая JSON-строка**
`{"12412": "MODEL_B", "91741": "MODEL_A"}` с сортированными ключами product_id.
Так перестановка массива не вызывает ложных изменений, а обмен моделей между
двумя продуктами не теряется. Отсутствующие/невычисленные классы причины отказа
в разрезах представлены `''` (в сравнении сам null сохраняется как `NULL`).
Дополнительно `PRODUCT_DETAILS_BEFORE`, `PRODUCT_DETAILS_AFTER` — JSON-объекты
`{product_id: {PD_MODEL, CUTOFF, REJECT_REASON, DECISION}}` для детализации.
Хранилище может сохранить расширения как JSON, обязательные поля остаются
доступны выданным проверкам в исходном виде. Это правило многопродуктовых
разрезов требует подтверждения участников при интеграции.

В тестах все пять выданных CHECK исполнены без изменения на тестовом адаптере
MartAPI; индексы и продакшен-хранилище остаются в зоне участника 2.

## Участникам 2 и 3: агрегированные факты counts

`pipeline.aggregate(comparison_rows) -> list[dict]`. Ровно поля демонстрационных
`task/examples/07_pivot_facts_demo.csv` / `08_pivot_facts_demo.json`:

| Поле | Тип и смысл |
|---|---|
| PREFIX, CLASS, SUFFIX, ARRAY_KEY, KEY | str, координаты атрибута |
| VALUE_ADJUSTED | str, ADJUSTED_BEFORE либо ADJUSTED_AFTER соответствующего SOURCE |
| DIFF_FLAG | int, 0/1, признак различия пары |
| SOURCE | str, машинные `BEFORE` / `AFTER` |
| CNT | int, количество присутствующих строк атрибутов в этом атомарном блоке |

Группировка — **все восемь полей кроме CNT**. Никаких APP_IDS или исходных
значений внутрь каждой записи counts не вкладывается. Срезы можно отображать
как `BEFORE (MASTER)` / `AFTER (BETA)` на уровне UI (в демо используются эти
подписи). Для источника используются машинные значения BEFORE/AFTER,
согласованные с нормализованным входом и кодом проверок.

Каждый SAME/VALUE_CHANGED создаёт две записи присутствия до группировки.
ATTRIBUTE_NEW — только AFTER, ATTRIBUTE_LOST — только BEFORE. Отсутствующий
атрибут не считается пустым значением; присутствующий пустой атрибут считается.
Сумма CNT всех фактов равна числу нормализованных строк BEFORE + AFTER.
Суммировать всё как «число заявок» нельзя: одна заявка содержит много атрибутов.
`total_apps` берётся из слоя разрезов, а не из суммы CNT.

Демо-факты содержат вымышленные 440 заявок; их CNT нельзя воспроизвести из пары
учебных ответов или четырёх samples. Проверены схема и инварианты агрегации,
а не выдуманное совпадение с этими демонстрационными числами.

## Участнику 3: переход от агрегата к заявке и атрибуту

```python
from pipeline import drill_down

cell = out['facts'][0]
filters = {key: value for key, value in cell.items() if key != 'CNT'}
members = drill_down(out['comparison'], **filters)
# Каждый member содержит APP_ID, PATH, ARRAY_KEY и поля ячейки, включая SOURCE.
app_ids = sorted({m['APP_ID'] for m in members})
leaf = members[0]
detail = next(row for row in out['comparison']
              if (row['APP_ID'], row['PATH'], row['ARRAY_KEY']) ==
                 (leaf['APP_ID'], leaf['PATH'], leaf['ARRAY_KEY']))
```

Можно передать часть полей факта для свёрнутой ячейки: фильтры соединяются
через AND, значения точные. CNT — метрика, его передавать как фильтр нельзя.
Неизвестный фильтр вызывает PipelineError. `fact_members(comparison)` выдаёт
плоскую развёртку принадлежности с `APP_ID`, `PATH` и всеми полями факта без CNT.
Это удобная основа дополнительного индексированного представления в mart.
Сам `drill_down` — эталонная процедура в памяти с линейным проходом; UI-запросы
на большом датасете участник 2 должен обслуживать SQL/индексами. Для сегментных
фильтров сначала отбираются APP_ID, затем по этому набору агрегируется comparison.

MartAPI из task/checks/README.md не меняется: для сводной участник 2 может
добавить отдельные запросы поверх тех же таблиц. Для проверки SOURCE/бакета
надо выбрать ADJUSTED соответствующего среза и исключить отсутствующие стороны.
Детали листа всегда запрашивать по полному первичному ключу, включая PATH.
