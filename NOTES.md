# Записка по итогам хакатона (черновик по шаблону организаторов)

Машина замеров: Windows 11, ноутбук (CPU 8 потоков, 16 ГБ RAM), Python 3.13,
DuckDB 2.0.0, однопроцессный uvicorn. Замеры: медиана 7 прогонов, клиент 127.0.0.1.

## 1. Стек и почему именно он

- **FastAPI + uvicorn** — сервер и API: быстрый запуск, нативная многопользовательность
  через подписанные cookie-сессии, фоновые прогоны в пуле потоков.
- **DuckDB** — хранение витрины (~290 тыс. строк на 2002 заявки): колоночная БД,
  SQL поверх файла, индексы по PATH/CHANGE_TYPE, окупается на агрегатах сводной.
  SQLite рассматривался как фолбэк, отказались в пользу единого стека с проверками.
- **Vanilla JS + CSS (без сборки, без CDN)** — фронтенд: отчёт должен работать
  офлайн на демо; сводная — собственный лёгкий pivot поверх агрегатов counts.
- **checkrunner** — изоляция пользовательского Python: Docker по
  умолчанию; для локального демо без Docker — subprocess-песочница
  (`CSD_TRUST_LOCAL_CODE=1`), код исполняется в отдельном процессе.

## 2. Как устроено хранение и почему

Вертикальный datamart по контракту [`task/docs/СХЕМА_ВИТРИНЫ.md`](task/docs/СХЕМА_ВИТРИНЫ.md):
`datamart` (APP_ID, PATH, ARRAY_KEY, SOURCE, VALUE, ADJUSTED_VALUE — UNION обеих
срезов), `attributes` (сопоставление: DIFF_FLAG, CHANGE_TYPE, первичный ключ
APP_ID+PATH+ARRAY_KEY), `segments` (16 полей слоя разрезов, строка на заявку),
представления `comparison` (горизонтальное до/после для drill) и `fact_members`
(вертикальные факты для сводной), материализованная `counts` (факты counts).
Сверено с эталоном жюри по открытому датасету: 0 расхождений по 2002 заявкам.

## 3. Где параллелится работа и почему

- Прогоны — в пуле потоков (`CSD_RUN_WORKERS`), несколько пользователей не мешают
  друг другу; короткие запросы отчёта не блокируются расчётом.
- Стадии внутри прогона последовательны: нормализация → сравнение → факты →
  загрузка в DuckDB → проверки. Параллелизм по заявкам внутри стадий возможен,
  но на данном объёме упор в диск/CPU уже не даёт выигрыша (см. замеры).

## 4. Как исполняем выданные процедуры из приложения

Контракт `CHECK = {id, label, params, entrypoint}`; MartAPI
(`rows/count/app_ids/segments/total_apps`) подаётся проверке как объект доступа.
Источник процедуры/проверки: встроенная / рабочая область (код в приложении) /
файл `.py` — выбор в UI, без изменения кода приложения. Песочница: Docker
(недоверенный код) или subprocess для доверенной локальной разработки.

## 5. Что делаем при догрузке новой порции данных

(не реализовано — опциональное требование) Архитектурно готово: витрина
пополняемая (PRIMARY KEY + UPSERT), факты counts пересчитываются поверх
fact_members; следующий шаг — инкрементальная загрузка новых APP_ID и
перезапуск затронутых агрегатов без полного прогона.

## 6. Узкое место: что замерили, что оказалось узким, что дало ускорение

Замеры прогона на двух машинах:

**Приведение и сравнение** (`pipeline.build_dataset`, 2002 заявки):
MacBook Air, Apple M4 (10 ядер), 16 ГБ RAM, macOS, Python 3.14 — медиана
3 прогонов: normalize 2.2 с, compare 1.6 с, facts 1.3 с, всего **5.2 с**
(детально: [pipeline/BENCHMARK_HIT.md](pipeline/BENCHMARK_HIT.md)). Windows-ноутбук команды (8 потоков,
16 ГБ, Python 3.13): тот же разбор — **19 с** (normalize 8.7, compare 5.4,
facts 4.4); полный цикл через сайт с загрузкой витрины и 5 проверками —
**~60 с**. Все операции в рамках одной машины — в планках «хорошо».

**Отчёт поверх витрины** (289 533 строки сравнения, 572 221 вертикальная
строка), HTTP-медианы: MacBook M4, 24 ГБ, DuckDB 2.0.0
(детально: [mart/benchmarks/REPORT.md](mart/benchmarks/REPORT.md)); в скобках — Windows-ноутбук команды:

| Операция | M4 (macOS) | Windows | Планка «хорошо» |
|---|---:|---:|---|
| Открытие/смена раскладки сводной | 1.2 с | ~1.0 с | ≤ 2 с |
| Фильтр /facts | 0.51 с | ~1.0 с | ≤ 1–2 с |
| Drill: ячейка → список → карточка | 0.54 с | ~0.6–1.0 с | ≤ 1 с |
| Карточка заявки | 0.24 с | 0.48 с | ≤ 1 с |
| Повторное открытие отчёта проверок | 0.17 с | ~0.5 с | ≤ 1 с |
| Скачивание HTML-отчёта | — | 0.32 с | — |

- Узкое место полного цикла — нормализация и сравнение JSON-документов
  (CPU-bound): 2.2 с из 5.2 с на M4. Отчёт быстрый за счёт материализованных
  фактов counts и индексов (attr_path/attr_change): сводная не сканирует
  витрину, а читает агрегаты.
- A/B-эксперимент с индексом `attr_app_lookup` выигрыша не дал — итоговая
  серия без него (честный отрицательный результат, `mart/benchmarks/`).
- Ловушка платформы: резолв `localhost → ::1` на Windows добавляет ~2 с к
  каждому запросу Python-клиента; на браузер и замеры macOS не влияет.

## 7. Что не успели и что было бы следующим шагом

- Инкрементальная догрузка данных (п.5) — опционально, не делали.
- Потоковое обновление отчёта во время прогона (сценарий 6) — опционально.
- Парсер произвольной глубины вложенности JSON в пользовательских процедурах.
- Параллельная нормализация заявок (multiprocessing) — на 20-тысячных прогонах.
