# DuckDB mart: интерфейс для участников 1 и 3

Реализованы только `mart/` и `checkrunner/`. Схемы организаторов и пять
выданных проверок не изменены. Python 3.11+, macOS/Linux (блокировки `flock`).

## Запуск и проверка

Из корня репозитория:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r mart/requirements-dev.txt
python -m pytest mart/tests checkrunner/tests -q
python -m mart.demo
python -m mart.demo --database /tmp/strategy-demo.duckdb --copies 21000
```

Последняя команда создаёт синтетический набор **294 000 атрибутов / 21 000
заявок**, запускает пять оригинальных проверок и печатает замеры. Это
реплика учебного CSV с заменой APP_ID, не полный датасет организаторов.
Разрезы демо заданы явно; пример не реализует нормализацию из `pipeline/`.

## Вход участника 1

```python
from mart import MartStore

store = MartStore("data/results.duckdb")
revision = store.save_run(
    run_id="RUN-001",
    comparison_rows=comparison_rows,  # Iterable[dict], контракт раздела 1 СХЕМА_ВИТРИНЫ
    segments=segment_rows,            # Iterable[dict], все поля раздела 2
    normalized_rows=normalized_union, # необязательно; см. ниже
    metadata={"configuration_id": "config-1"},
)
```

* `APP_ID`, пути, ARRAY_KEY и значения — строки. Ведущие нули сохраняются.
  Отсутствующее значение — `""`, JSON null внутри ответа — строка `"NULL"`,
  если так определено нормализатором. `CHANGE_TYPE` отличает отсутствие
  атрибута от присутствующего пустого значения.
* `DIFF_FLAG` и `DECISION_CHANGED` — целые 0/1, не строки и не bool.
  Смена значения проверяется по VALUE, независимо от бакета.
* В разрезах обязательны все поля схемы, неизвестные значения допустимы
  как `None`/`""`. `PRODUCTS` — строка уникальных продуктов через `;`, как
  ожидает выданная проверка. SCORE_OKB принимается также числом и хранится
  строкой. Одна строка разрезов на APP_ID, даже если у заявки нет атрибутов.
* Уникальность атрибута: `(APP_ID, PATH, ARRAY_KEY)`. Пустой APP_ID/PATH,
  дубли и противоречивые признаки приводят к `ValueError` до записи.
* `normalized_rows`, если передан, содержит `APP_ID, PATH, ARRAY_KEY,
  SOURCE, VALUE, ADJUSTED_VALUE`. SOURCE принимает `BEFORE`/`AFTER` и
  `BEFORE (MASTER)`/`AFTER (BETA)`. Проверяются точные значения, бакеты,
  наличие строк и уникальность. PATH передаётся явно: восстанавливать его
  из SUFFIX/KEY небезопасно, особенно для массивов скаляров. Старый учебный
  UNION не содержит PATH; присоединение PATH показано в тестовой фикстуре.
* Если нормализованный UNION не передан, вертикальные строки восстанавливаются
  без потерь из сравнения и CHANGE_TYPE. Нормализация исходного JSON в этом
  модуле не выполняется. Пользовательские результаты сравнения не подменяются.
* Повторный `save_run` атомарно заменяет **весь** прогон и инвалидирует старый
  отчёт проверок. Это не append API. Порционную загрузку интегратор должен
  собирать до финального сохранения; показ частичного отчёта ТЗ не требует.

## Почему хранение вертикальное

Подробное `02_ОПИСАНИЕ_ЗАДАЧИ.md`, раздел «Что значит отчёт и сводная таблица»,
требует вертикальный datamart. Схема проверок требует горизонтальные поля.
Оба требования соблюдены без изменения контракта:

* `datamart` хранит VALUE/ADJUSTED_VALUE и SOURCE вертикально;
* `attributes` хранит идентичность, структуру пути и результат сопоставления;
* `comparison` — SQL view, собирающий горизонтальные строки для MartAPI;
* `segments` хранит разрезы, `counts` — материализованные агрегированные факты;
* `fact_members` связывает факты с APP_ID, PATH и ARRAY_KEY для переходов;
* `runs` хранит revision/metadata, `reports` — единый JSON-отчёт с диагностикой.

Внутренний `run_id` не добавляется в строки публичных контрактов. Есть
составные первичные ключи и индексы по `(run_id, PATH)` и
`(run_id, CHANGE_TYPE)`. SQL использует параметры, имена колонок ограничены
белыми списками. Блокировка файла и потоков сериализует подключения,
включая запись из разных процессов. Это локальное хранилище, не
распределённая БД для разных серверов/NFS.

## MartAPI организаторов

```python
mart = store.for_run("RUN-001")  # неизвестный прогон: KeyError
mart.rows(path=["a.b", "a.c"], diff_flag=1)
mart.count(change_type=["ATTRIBUTE_NEW", "ATTRIBUTE_LOST"])
mart.app_ids(path_prefix="decisionResult.")  # уникальные, отсортированные
mart.segments()
mart.total_apps()
```

Поддержаны все фильтры `task/checks/README.md`, комбинируются через И:
`path`, `path_prefix`, `key`, `array_key`, `diff_flag`, `change_type`,
`value_before`, `value_after`, `app_ids`. Пустой список ничего не выбирает.
Префикс буквальный: `%` и `_` не SQL wildcards. Неизвестный фильтр — ошибка.
Возврат rows/segments — список словарей (реализация Iterable из контракта).

## Функции для участника 3

```python
mart.summary()  # total_apps, changed_apps, decision_changed_apps
facts = mart.aggregates()  # схема task/examples/07_pivot_facts_demo.csv
mart.aggregates(
    ["KEY", "SOURCE", "DIFF_FLAG", "PARTNER_TYPE"],
    filters={"PATH": "decisionResult.decision"},
    segment_filters={"product": "CASH_LOAN", "DECISION_CHANGED": 1},
)
members = mart.drill_down(filters={k: v for k, v in facts[0].items() if k != "CNT"})
# members: [{APP_ID, PATH, ARRAY_KEY}, ...]
mart.page(limit=100, offset=0, app_ids=[m["APP_ID"] for m in members], diff_flag=1)
mart.application("APP-1", path="decisionResult.decision", array_key="")
store.run_info("RUN-001")
report = store.get_check_report("RUN-001")  # None, если проверки ещё не запускали
store.get_check_results("RUN-001", check_id="external_score_drift", result="FAIL")
store.get_check_results("RUN-001", app_id="APP-1")
```

У `aggregates`/`drill_down` имена фильтров **UPPERCASE** — поля факта:
`PREFIX, CLASS, SUFFIX, ARRAY_KEY, KEY, VALUE_ADJUSTED, DIFF_FLAG, SOURCE,
PATH, CHANGE_TYPE, APP_ID`. Разрезы фильтруются через `segment_filters`
по полям схемы; специальный `product` — точное вхождение в список PRODUCTS,
а не совпадение подстроки. Для группировки допустимы измерения факта,
PATH/CHANGE_TYPE и все разрезы кроме APP_ID. Пустая/неизвестная раскладка
отклоняется. Фильтры допускают скаляр либо список значений.

SOURCE фактов — `BEFORE (MASTER)`/`AFTER (BETA)`, как в учебном CSV.
SOURCE проверок — строго `BEFORE`/`AFTER`, как в контракте проверок.
`CNT` — **число уникальных заявок в группе**. При изменении раскладки
пересчитывается DISTINCT APP_ID из membership-слоя, а не SUM(CNT), чтобы
не считать одну заявку несколько раз. Новые атрибуты дают факт только
AFTER, потерянные — только BEFORE. Drill-down использует те же фильтры.
`drill_down` возвращает полный список связей; `page` ограничивает строки
сравнения (1–10000). На очень больших группах API-слою следует ограничивать
передачу/визуализацию списка связей.

Унифицированный отчёт и исполнение описаны в [../checkrunner/README.md](../checkrunner/README.md).
`APP_IDS` в проверке — ограниченная выборка по app_ids_limit, не полный
список всех срабатываний. `ARGUMENT` может быть именем продукта/модели,
а не PATH; нельзя автоматически превращать любой ARGUMENT в путь атрибута.

Веб-слой обязан проверить владельца run_id и доступ к выбранному `.py`
**до вызова этих функций**. Этот модуль не реализует HTTP/auth. Длительные
`save_run`/`CheckRunner.run` запускаются в фоновой задаче, не в event loop.
`on_event` позволяет передавать прогресс в существующий журнал приложения.

## Статус передачи контрактов

Контракты организаторов сохранены. Этот файл и README checkrunner —
предложение интерфейсов для участников 1 и 3 и артефакт передачи через
ветку/PR. Подтверждения от участников в этой сессии не получено; утверждать,
что интеграционный контракт согласован или приложение подключено, нельзя.
Ни pipeline/, ни api/, ни frontend/ не изменены.

## Проверка и производительность

Измерено на macOS ARM64, Python 3.13.4, DuckDB 2.0.0, одним запуском
`python -m mart.demo --copies 21000` (тёплый локальный диск):

| Операция | Секунды |
|---|---:|
| Сохранение 294 000 строк сравнения / 546 000 вертикальных значений | 5.985 |
| Верхняя сводка | 0.008 |
| Чтение материализованных counts | 0.007 |
| Смена раскладки | 0.048 |
| Фильтр продукта | 0.044 |
| Drill-down по решению | 0.025 |
| Конкретный атрибут заявки | 0.009 |
| Пять проверок, включая создание снимка | 7.735 |
| Повторное чтение отчёта | 0.007 |

У синтетики всего 26 разных фактов: это проверка объёма строк, не замена
бенчмарку высокой кардинальности на настоящем прогоне 2002 заявок.
Полный датасет и нормализатор участника 1 пока не интегрированы. Основная
стоимость — массовая запись/создание снимка, а не фильтры. Снимок строится
один раз на набор проверок; каждой проверке передаётся его отдельная копия.
